## 1. 维度一：无障碍（WCAG 2.2 AA）

### 1.1 【P0·A1】透明态页头导航文字对比度崩溃（实测 1.33:1）

计划 §4.2 要求首页 `scrollY < 24px` 时页头为「半透明通透态」（无背景、仅微光描边），§5.1 未给该状态任何对比度验收。独立复算（通道域 alpha 复合，与 CSS 渲染一致）+ 壁纸实测：

- 页头区（垂直 0%–12%）壁纸平均亮度 L≈0.25–0.40、最亮像素 L≈1.00；
- 计划 §4.3 蒙版顶端仅 0.40 alpha；
- 导航文字沿用 `--color-text-muted: #94a3b8`（现状 SiteHeader 即此令牌），对 0.40 蒙版复合背景：
  - 平均像素（L≈0.35）：**2.31:1**；
  - 高光采样 `#FDE047`：**1.33:1**；
  - 近白像素（L≈1.0）：**1.04:1** —— 三种情形全部 < 4.5:1；
- 即便导航改用白字 `#f8fafc`：平均 5.65:1 ✅，但高光采样 `#FDE047` 处 **3.26:1**、近白处 **2.54:1** ❌ —— 因近白像素遍布整个页头区，白字同样不能保证达标（导航文字要 4.5:1 需 α ≥ ~0.9，即近不透明 plate）。

修复方向（写入计划）：透明态页头必须自带**独立 scrim**（顶部渐变暗化或最小 blur），并以「合成对比度 ≥4.5:1（正文级导航链接）」为验收。

### 1.2 【P0·A2】Hero 文字合成对比度声称被壁纸实测否定（14.5:1 / 9.8:1 失实）

计划 §5.1 声称「正文白字 14.5:1」「大字金色渐变 9.8:1」。该数值只对**不透明纯底**成立；对计划自身的合成场景（壁纸 × §4.3 蒙版 0.4→0.65→0.98）不成立。R2 新增直接证据——对源壁纸 `3840x2160px_D_suisen.png` 全图像素采样（纵向 40 行 × 横向 40 列）：

| 垂直带                 | 平均亮度 L | 行内最亮像素 L |
| ---------------------- | ---------- | -------------- |
| 0%–12%（页头区）       | 0.25–0.40  | **1.00**       |
| 20%–40%（标题/焦点区） | 0.33–0.40  | **1.00**       |
| 40%–70%（引言/芯片区） | 0.33–0.44  | **1.00**       |
| 70%–90%                | 0.29–0.36  | 0.97–1.00      |
| 90%–95%                | 0.18–0.19  | ~1.00          |
| 95%+                   | 0.05       | 0.14–0.47      |

结论：**这是一张逆光高亮壁纸，从顶部到 90% 高度都散布近白像素（L≈0.97–1.00）**，计划声称的「焦点区」恰在其中。合成复算（WCAG 2.2 相对亮度，**通道域** alpha 复合，与 CSS 实际渲染一致；三档背景采样：平均像素 L≈0.35–0.40 / 高光采样 `#FDE047` L≈0.74 / 近白像素 L≈1.0）：

| 场景                           | 计划声称 | 复算·平均像素 | 复算·#FDE047 | 复算·近白像素 | 阈值        | 判定                     |
| ------------------------------ | -------- | ------------- | ------------ | ------------- | ----------- | ------------------------ |
| 白字 on 0.40 蒙版（页头带）    | —        | 5.65          | 3.26         | **2.54**      | 4.5         | ❌                       |
| 白字 on 0.55 蒙版（中带/引言） | ≈14.5:1  | 7.47          | 5.12         | **4.19**      | 4.5         | ❌（近白不达标）         |
| 白字 on 0.65 蒙版（中下带）    | —        | ~9.6          | 7.05         | **5.95**      | 4.5         | ✅ 最坏通过（仍非 14.5） |
| 白字 on 0.98 蒙版（底带）      | —        | —             | 18.1         | ~18.0         | 4.5         | ✅（仅底带窄条）         |
| 金色大字 on 0.55（标题区）     | 9.8:1    | —             | 2.49         | **2.04**      | 3.0（大字） | ❌                       |
| 金色大字 on 0.65               | —        | —             | 3.43         | **2.90**      | 3.0（大字） | ❌（近白）               |
| 渐变珊瑚端 `#ff6b4a` on 0.65   | —        | —             | **2.62**     | **2.21**      | 3.0（大字） | ❌                       |
| 导航 muted `#94a3b8` on 0.40   | —        | 2.31          | **1.33**     | **1.04**      | 4.5         | ❌                       |
| 亮色串用 `#1c1917` on 0.65     | —        | —             | **2.37**     | —             | 4.5         | ❌（见 A3）              |

**反推所需蒙版 α**（对近白像素的通道域求解）：正文白字 4.5:1 需 α ≥ **0.58–0.60**；金色大字 3:1 需 α ≥ **0.68**；珊瑚端 3:1 需 α ≥ **0.75**；导航 muted 4.5:1 需 α ≥ **~0.90**（近不透明 plate）。即：计划 0.40 / 0.55 两档在近白像素下均不达标（2.54 / 4.19），文字区蒙版至少须以 0.65 起步、导航区须近不透明；渐变标题的珊瑚端即使垫到 0.75 蒙版也只是勉强 3:1——**与高光壁纸实质冲突，必须换色或改实色大字方案**。

修复方向（写入计划，闭合 R1-P0-1）：

1. 阶段 0 必须先做壁纸亮度分布采样（本报告方法可直接复用），再据实测校准蒙版 stops 与文字区布局；
2. 文字块增加**局部径向/线性 scrim**（正文 ≥4.5:1、大字 ≥3:1 按近白像素验收）；
3. 渐变标题两端色值需重选（珊瑚端太亮）或改为「实色大字 + drop-shadow 辉光」；
4. §5.1 全部改为合成对比度验收项并脚本化（见 T3）。

### 1.3 【P0·A3】亮色主题 Hero 颜色契约仍缺失（主题串用 = 2.37:1）

R1 已提（P0-3），计划未修订：§4.3 蒙版为固定深色 `rgba(10,12,22,…)`，但 Hero 文字用哪套令牌未定义。若亮色主题下 Hero 沿用 `--color-text-primary: #1c1917`：

- 复算：`#1c1917` on 0.65 蒙版 × 高光 = **2.37:1**（R1 用更暗复合得 1.21:1，均远低于 4.5:1）；
- 现有 axe 测试在 headless 下默认 `prefers-color-scheme: light`，亮色主题正是被测状态（见 T7），而 axe 又测不到背景图上的文字（见 T3）——**这条失败路径恰好落在自动化盲区里**。

修复方向：新增「Hero 场景强制 light-on-dark 令牌作用域」章节（两种主题下 Hero 内文字/页头统一用暗色系专用令牌），并配合成对比度验收。

### 1.4 【P1·A4】焦点指示两条 <3:1，且与 §5.1 自相矛盾

- 暗色 `--color-focus-ring: rgba(245,158,11,.45)` 复合后 = `#784f17`，对 `#0f1221` **2.62:1**；
- 亮色 `rgba(194,65,12,.35)` 复合后 = `#e8baa5`，对 `#fdfbf7` **1.69:1**；
- §5.1 声称「2px 实线夕阳金」（即 `--color-focus`，暗 8.66:1 / 亮 5.01:1 ✅）与 §2.2 保留的半透明 ring 令牌矛盾；
- 计划宣称「严格满足 WCAG 2.2 AA」，但 **2.4.11（焦点不被遮挡，AA）与 2.4.13（焦点外观，AAA）均未被覆盖**。R2 补充：固定/吸顶页头（§4.2 改为 fixed 后）在滚动时可能完全遮住键盘焦点项——需 2.4.11 专项验证（现有 `scroll-padding-top` 只解决锚点，不解决焦点）。

修复方向：ring 令牌改实色 `--color-focus` 或 α ≥ 0.7；组件统一 `outline`/`box-shadow` 走该令牌；补 2.4.11 焦点遮挡验证项。

### 1.5 【P1·A5】`--color-text-dim` 三处真实正文级消费点均不达标（实测复算）

独立复算：`#64748b` on `#0f1221` = **3.91:1**、on `#13172b` = 3.72:1、on `#161a30` = 3.60:1。仓库实测消费点（grep 定位）：

- `home.css:179` `.pagination-link`（0.88rem 数字正文）；
- `home.css:466` `.tag-badge`（0.88rem 标签正文）；
- `PostCard.astro:304` `.post-card-tag-more`（0.72rem）。

三处均为常规尺寸文字（非大字），需要 4.5:1。计划将原值原样带入新系统（§2.2 暗色 `--color-text-dim: #64748b`），**现状缺陷被计划背书**。建议暗色改 `#7d8cb0`（复算 5.5:1）并与 secondary 拉开层级；亮色 `--color-text-dim` 与 `--color-text-secondary` 同为 `#44403c`（层级塌陷，R1 已提）。

### 1.6 【P1·A6】skip-link 目标改写与现契约冲突 + 锚点焦点管理缺失

- 计划 §5.1「Tab 跳至主要内容 `#latest-posts`」：现状契约是 `#main-content`（`BaseLayout.astro:112` skip-link + `main id="main-content" tabindex="-1"`），且有测试锁定（`client-behavior.spec.ts:131-141` 断言 Enter 后 `#main-content` 获得焦点）。改跳 `#latest-posts` 既破坏测试，也不符合语义（main 才是主要内容容器，Hero 属装饰性区域）；
- 下滚指示器 `<a href="#latest-posts">`：无 `:target` 样式、目标无 `tabindex="-1"`，键盘触发后焦点留在箭头链接上（WCAG 2.4.3 焦点顺序合理 + 2.4.7 可见焦点）。

修复方向：skip-link 保留 `#main-content`；锚点目标补 `tabindex="-1"` + `:target` 焦点样式（现状 `scroll-padding-top: calc(var(--header-height) + 1.5rem)` 已存在且够用，计划应声明继承而非另起炉灶）。

### 1.7 【P1·A7】Topic Chips：6 个真实链接 → 4 个纯文本（键盘/导航入口回归）

现状 `Hero.astro:58-68` 的 6 个 chips 是经 `buildTagPath()` 映射到真实 tag 的 `<a>`（含「生成式超分辨率→超分辨率」「信号与系统」）；计划 §4.3 的 4 个 chip 在示例中为**纯文本**（无 href），且 label 与真实 tag 不一致（「深度学习理论」→ 实际 tag「深度学习」）。键盘用户与屏幕阅读器将失去 6 个标签导航入口，且删除「超分辨率」「信号与系统」两个主题未在任何章节声明。R1 已提（P1-4），R2 从键盘可访问性角度确认：**若 chips 改为纯文本，必须声明为装饰性并 `aria-hidden`，且不得再用 `div` 冒充可点元素；若保留链接，须给出 label→tag 映射表**。

## 2. 维度二：性能指标

### 2.1 【P0·P1】6.02 MB 原图直出与「LCP ≤ 2.5s」门禁必然互斥

实测：源 PNG `3840x2160px_D_suisen.png` 文件大小 **6.02 MB**（Get-Item 实测，非估算）。

- 传输账：Lighthouse Fast-4G 有效下行 ≈ 200 KB/s → 单图传输 ≈ **30s**；真实 4G（≈1.25 MB/s）≈ **4.8s**；两者均远超计划自设 LCP ≤ 2.5s 门禁。即便 CDN+HTTP/2 也不能把 6 MB 压进 2.5s 的 4G 预算；
- 体积账：仓库现有全站首包 JS 预算 `audit-bundle.ts` 为 **24 KB gzip 总预算 / 8 KB 单文件**——该 PNG 约为全站 JS 预算的 **250 倍**，将占据页面权重 ~99.6%；
- 解码账：3840×2160 解码位图 ≈ 8.3 MP × 4B ≈ **33 MB**，低端移动端解码 + 全屏绘制 + 滚动重绘存在掉帧风险；
- Chrome 将 `background-image` 计入 **LCP 候选元素**，故 LCP 元素就是这张图——6 MB 原图 = 门禁自杀；
- `public/` 与 `astro-public/` 中的资产**不经过 Astro 图片管线**（`publicDir: "astro-public"` 实测），复制即原样部署，无压缩/无内容哈希 → 缓存失效策略也缺失。

修复方向（闭合 R1-P0-2，写入 §3.1）：产出 AVIF（主）/ WebP（备）/ PNG（兜底）三源，按断点分级（移动端 1080p ~300–400 KB、桌面 4K ≤ 2 MB 量级）；首选 `<img>` + `srcset/sizes` + `fetchpriority="high"`（而非纯 CSS 背景）以利 `decoding`/`eager` 控制；保留底色占位 + 增加 LQIP/dominant-color 渐显；`public/images/` 备份动作删除（与 Hexo 隔离冲突，R1 已提）。

### 2.2 【P1·P2】preload 作用域错误：全站每页预载 4K 图

计划 §3.1 在 `BaseLayout.astro` `<head>` 中无条件输出 `<link rel="preload" as="image" … fetchpriority="high">`。实测 `PostLayout.astro:6` 继承 `BaseLayout` → **文章页/归档页/搜索页每页都会预载 6 MB 图**，与正文内容抢带宽（对非首页流量是纯浪费）。且该写法无 `imagesrcset/imagesizes` 或 `media` 条件，多源方案落地后 preload 也无法命中正确变体。

修复方向：preload 仅首页条件输出（`isHome` prop），且携带 `imagesrcset/imagesizes` 匹配 LCP 变体，或改为 `<img fetchpriority="high">` 由浏览器原生调度。

### 2.3 【P1·P3】无测量协议：无基线、无预算表、无重测、无 INP

计划 §6 只有「跑命令」门禁，性能目标（0-CLS / LCP ≤ 2.5s）**没有任何测量与验收手段**：

1. 无基线采集协议（阶段 0「基准测试」未定义工具、设备、网络条件、样本数、百分位——LCP 应按 p75 且区分设备等级；Moto G4 级 vs 桌面级必须分开预算）；
2. 无合成（Lighthouse CI）与 RUM（web-vitals/CrUX）双轨；
3. **INP 完全缺位**：新 Hero 的磁吸位移（`pointer-controller` 已存在）、渐变辉光、`backdrop-filter: blur(12px)` 全宽吸顶页头在滚动/交互时都有主线程成本，计划对 INP 只字未提（预算建议：INP ≤ 200ms p75，与 CWV Good 阈值一致）；

5. 无预算断言进 CI：现有 `audit:bundle` 只查 `dist/_astro/*.js`（gzip 24 KB），**对 6 MB 图片完全无感**（盲区）。

## 3. 维度三：响应式矩阵

### 3.1 【P0·R1】断点矩阵缺口：320px 无档位、481–767px 整段空档、4K 档位过小

- §0 声称「支持 320px~4K」，§5.2 矩阵却从 **360px** 起，320px（如 iPhone SE 一代、Galaxy Fold 外屏 280px）无任何策略；现状 `Hero.astro:570` 尚有 `≤25rem`（400px）档位，新计划反而回退；
- 矩阵跳档：360–480px 之后直接 768–1023px，**481–767px 全空**（600px 小平板、667×375 横屏手机、640px 视口无字号/间距/指示器策略）；
- ≥1440px 合并「4K/宽屏」单档 3.2rem：3840px 屏上 3.2rem 视觉占比不到 1440px 屏的 40%，且固定 rem 阶梯跳变；建议 `clamp()` 流式字号（如 `clamp(2.2rem, 6vw, 6rem)`）并为 4K 单独设档。

### 3.2 【P1·R2】短视口与 `100svh` 兜底缺失

- §5.2 仅写「首屏使用 100svh」，无 `100vh` 前置兜底（svh 需 Safari ≥ 15.4 / Chrome ≥ 108，低版本将整条声明丢弃 → Hero 高度塌陷）；应写 `min-height: 100vh; min-height: 100svh;`（用 `min-height` 而非 `height`，防内容超高裁切）；
- 高度维度完全缺席：iPhone SE（375×667）、横屏手机（高度 ~390px）、桌面窄高窗（如 1024×600）下，大标题×2 行 + 引言 + chips + 指示器在 `100svh` 内会溢出——需 `@media (max-height: 700px)` 压缩档与 `overflow` 策略。

### 3.3 【P1·R3】背景定位自相矛盾 + 竖屏裁切断言无证据

- §3.1.2 定义单一 `background-position: center 25%`，§5.2 又说平板「壁纸聚焦中心」——同一资产不可能同时满足，需给出按断点的 `background-position` 媒体条件表；
- 9:16 竖屏 `cover` 裁切推导：390×844 视口下图片按高度缩放至宽 ≈ 1500px，**横向裁掉 3840−1500 ≈ 61%**；壁纸实测高光像素遍布全宽（每行 MaxL≈1.00），无法确认「人物居中」；计划断言「人物居中且视线聚焦点自然」在 16:9/16:10/4:3/9:16 四个比例下均**未经验证**（R1-P2-4/1.3，仍开放）。建议阶段 0 用现有 `capture:ui-baseline` 管线出四断点裁切预览并反推 `object-position` 响应式值；
- 「黄金分割定位」命名不实：25% 是上部聚焦位，不是黄金分割（0.618）。

### 3.4 【P1·R4】大标题横向溢出风险无保障（360px 与 200% 缩放双重）

- 新 h1「WELCOME TO ENTROPYXI BLOG !」若用 `--font-display`（等宽），28 字符 × 0.6em × 2.2rem ≈ **592px** > 360px 视口（减去 `main` 内边距后更紧）——计划只说「拆行堆叠」，未定义 `text-wrap: balance`/`overflow-wrap` 与逐断点字号上限；

## 7. 验证方法附录

1. **对比度复算**：自写脚本按 WCAG 2.2 相对亮度公式（sRGB 线性化）对计划 §2.2 全部令牌对独立计算；半透明令牌（scrim/glass/focus-ring）按**通道域（sRGB 编码域）alpha 复合**后计算，与 CSS 实际渲染一致。关键值：暗 focus-ring 复合 2.62:1、亮 1.69:1、text-dim 3.60–3.91:1、亮 coral 3.44:1、亮 inline-code on 暗块 2.39:1（与 R1 复算一致）。
2. **壁纸亮度采样**：`System.Drawing` 直接读取源 PNG（3840×2160），纵向 40 行 × 横向 40 列采样相对亮度；结果：0%–88% 垂直带平均 L≈0.25–0.44，**每行最亮像素 L=0.97–1.00**；95% 以下才转暗（L≈0.05）。源文件大小实测 6.02 MB。
3. **测试实跑**：`npm run test:e2e` → **38/38 通过（24.8s）**；`npm run test:unit -- --run` → **32/32 通过**；破裂断言按 spec 行号逐条定位。
4. **仓库核验**：package.json（check 9 步）、playwright.config.ts（7 项目 testMatch）、audit-bundle.ts（仅 JS 24 KB）、audit-output.ts（仅文章页）、BaseLayout/PostLayout（preload 作用域）、SiteHeader（sticky 4rem→3.5rem）、tokens.css（font local-first、90+ 非色彩令牌）、global.css（scroll-padding-top、main 约束）、client-behavior/client-matrix/home/accessibility specs（断言清单）。
